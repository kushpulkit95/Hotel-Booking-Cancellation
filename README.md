# Hotel Booking Cancellation Prediction

A machine learning application that estimates how likely a hotel booking is to be cancelled. Enter a few booking details in the web app and get a cancellation probability, a risk level (Low / Medium / High) and practical tips.

The project covers the full path from raw data to a working app: exploratory analysis, data cleaning, leakage prevention, preprocessing and feature selection, model comparison, threshold tuning, a FastAPI backend and a React frontend.

## Why this matters

Cancellations leave rooms empty and make planning harder. If a hotel can tell which bookings are likely to be cancelled, it can ask for deposits, send reminders or plan a small overbooking buffer for those dates.

## Results

The task is binary classification: predict `is_canceled` (1 = cancelled). After cleaning, about 27% of bookings are cancellations, so always predicting "not cancelled" already scores 72.7% accuracy. Accuracy alone is therefore not a useful measure, and the results below focus on the cancelled class.

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| Logistic Regression (baseline) | 0.802 | 0.676 | 0.527 | 0.592 | 0.856 |
| Random Forest (default 0.5 threshold) | 0.840 | 0.748 | 0.623 | 0.680 | 0.902 |

The final model is the Random Forest with the decision threshold lowered to 0.35. The threshold was chosen on out-of-fold predictions from the training set only, so the test set stayed untouched. On the held-out test set it gives:

| Metric (cancelled class) | Value |
|---|---|
| Recall | 0.79 |
| Precision | 0.65 |
| F1 | 0.71 |
| ROC-AUC | 0.902 |

Lowering the threshold trades precision for recall: the model now catches about 79% of real cancellations, at the cost of roughly one in three flagged bookings not actually cancelling. A hotel that dislikes false alarms more than empty rooms can raise the threshold.

## Setup

You need Python 3.10 or newer and Node.js.

**1. Clone and create the environment**

```powershell
git clone <your-repo-url>
cd Hotel-Booking-Cancellation
python -m venv .venv
.venv\Scripts\Activate.ps1          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

**2. Get the dataset**

Download the *Hotel Booking Demand* dataset from Kaggle and save it as `data/hotel_bookings.csv`. The file is git-ignored, so it is not part of the repository.

**3. Train the model**

```powershell
python -m src.train
```

This takes several minutes. It prints the model comparison, feature counts, threshold tuning and test results, then saves `model/hotel_cancellation_model.pkl` (about 48 MB). Use `python -m src.train`, not `python src/train.py`, so that imports from `src` work.

`model/defaults.json` is already included. If you change the cleaning code, regenerate it with `python -m src.make_defaults`.

**4. Install the frontend dependencies**

```powershell
cd frontend
npm install
cd ..
```

## Running the app

Open two terminals in the project root.

**Terminal 1: backend**

```powershell
python -m uvicorn backend.main:app --reload
```

Wait for `Application startup complete`. Interactive API docs are at http://127.0.0.1:8000/docs.

**Terminal 2: frontend**

```powershell
cd frontend
npm run dev
```

Open http://localhost:5173. Use one of the example buttons to see a result straight away, or fill in your own booking and click **Estimate cancellation risk**.

If the page says it cannot reach the prediction service, the backend is not running. Restart the backend whenever you retrain, because it loads the model only at startup.

## API

| Method | Path | Description |
|---|---|---|
| GET | `/` | Short status message |
| GET | `/health` | Returns `{"status": "ok"}` |
| POST | `/predict` | Returns the cancellation probability for one booking |

Example request:

```json
{
  "hotel": "City Hotel",
  "arrival_date": "2026-07-15",
  "lead_time": 200,
  "stays_in_weekend_nights": 2,
  "stays_in_week_nights": 3,
  "adults": 2,
  "deposit_type": "Non Refund",
  "market_segment": "Online TA",
  "previous_cancellations": 0,
  "total_of_special_requests": 0,
  "adr": 100,
  "country": "PRT"
}
```

Example response (values will vary slightly between training runs):

```json
{
  "cancellation_probability": 0.6995,
  "will_cancel": true,
  "prediction": "LIKELY TO BE CANCELLED",
  "threshold": 0.35
}
```

Accepted values: `hotel` is `City Hotel` or `Resort Hotel`; `deposit_type` is `No Deposit`, `Non Refund` or `Refundable`; `market_segment` is one of `Aviation`, `Complementary`, `Corporate`, `Direct`, `Groups`, `Offline TA/TO`, `Online TA`; `country` is a 3-letter code such as `PRT`. Ranges: `lead_time` 0 to 800, weekend nights 0 to 20, weekday nights 0 to 50, `adults` 1 to 10, `previous_cancellations` 0 to 30, special requests 0 to 5, `adr` 0 to 1000. Requests outside these limits get a 422 response that names the field.

The form asks for 11 details. The other model inputs (meal plan, booking agent, customer type and so on) are filled with the most common or median value from the training data, stored in `model/defaults.json`.

## How the data is prepared

All of this happens in `src/preprocessing.py`. The cleaning uses only fixed rules and constants, so it is safe to run before the train/test split. Everything that learns from the data (scaler, encoder, feature selectors) lives inside one scikit-learn pipeline that is fitted on the training set only. The backend loads that same pipeline, so training and prediction cannot drift apart.

| Step | What is done | Why |
|---|---|---|
| Invalid rows | Remove `adults > 10`, `adr < 0`, `adr > 1000` | 20 to 55 adults, a negative price and a 5,400 price (next highest is 510) are errors. Other extreme values are genuine and kept |
| Leakage | Drop `reservation_status`, `reservation_status_date` | They record how the booking ended, which is unknown at prediction time |
| Duplicates | Drop exact duplicate rows (119,390 to 87,124 rows after all cleaning) | Prevents identical rows landing in both train and test |
| Not known at booking | Drop `assigned_room_type`, `booking_changes`, `arrival_date_year` | Decided after booking, or the data only covers 2015 to 2017 |
| Missing values | `children` to 0, `country` to "Unknown", `agent` to a "0" category, `company` to a `has_company` flag | Missing means "none / not recorded"; `company` is about 94% missing |
| Binary and ordinal encoding | `hotel` as 0/1; month in calendar order; meal as none < breakfast < half board < full board | These have a natural order or only two values |
| One-hot encoding | Deposit type, market segment, distribution channel, customer type, room type, country, agent | No natural order. Categories under 1% of rows are grouped into one column |
| Binning | Lead time (0-7, 8-30, 31-90, 91-180, 181-365, 365+ days), previous cancellations (0, 1, 2+), waiting-list flag | Domain-defined, meaningful ranges |
| Transformation | `log1p` on 10 skewed columns, then standardise numeric columns | Reduces right skew; needed for Logistic Regression |
| Feature selection | Variance threshold, correlation filter (above 0.9), Random Forest importance | 75 encoded features reduced to 33 |

Feature counts through the pipeline: 31 raw columns, 26 after cleaning, 75 after encoding and binning, 70 after the variance threshold, 65 after the correlation filter and 33 after importance selection.

## Limitations

- **Random split on time-ordered data.** The bookings span 2015 to 2017, and a real deployment predicts the future. A time-based split would be a more honest estimate and would probably score lower.
- **Narrow data.** Two hotels in Portugal. The model should not be assumed to generalise to other hotels or countries.
- **The non-refundable deposit pattern looks like a dataset quirk.** Almost all such bookings are cancelled in this data, which is unusual in real life, so this strong signal may not carry over.
- **Duplicate removal is a judgement call.** The duplicates were mostly cancellations, so removing them moved the class balance from about 63/37 to 73/27 and weakened the apparent long-lead-time effect.
- **Default values for hidden fields.** The app assumes a typical booking for anything the form does not ask, so estimates are only as good as that assumption.
- **Limited tuning.** One Random Forest configuration and a single split, with no hyperparameter search. The probabilities are estimates, not guarantees.
